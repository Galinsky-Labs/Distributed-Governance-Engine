# Table editing

Select one cell to show Table layout in the side panel. Insert rows above/below or columns left/right, delete a row/column, or delete the table. Tables remain rectangular and are limited to 20 rows and 10 columns. The last row or column cannot be deleted separately. Removing the only table in a required body leaves an empty paragraph. There are no merged cells, multi-cell structural selections, or resizing controls.

Tab and Shift+Tab move between cells. Tab at the last cell appends a row within the limit when editing is permitted. Shift+Tab from the first cell and Tab at the size limit leave normal browser keyboard navigation available. Navigation alone does not create a document revision. Each structural command forms one undo group; the existing editor history or shared Yjs undo manager handles undo/redo.

Inserts and deletes operate on the selected rows/cells rather than replacing the entire table. Surviving semantic IDs, text, formatting and Yjs objects remain intact. New blocks receive new UUIDs. This matters when another participant edits a surviving cell while the row command is in flight. Deleting referenced blocks uses existing draft diagnostics; finalization still rejects unresolved references. Public-input, adopted, published and signed source cannot be edited directly, and view-only participants cannot submit edits.

The authenticated browser test uses the actual application, local TLS 1.3 WSS hub, signed fixture OIDC login and PostgreSQL-compatible PGlite store. Two separately authenticated members join one public draft. One browser deliberately delays incoming peer updates while the peer types and obtains a durable save acknowledgment. The first browser inserts a row from its older view, releases the delayed update, and both converge with the peer text preserved. Leaving live editing and reopening verifies the stored result. The delivery fault injection wraps native WebSocket listeners; it does not substitute a relay or persistence implementation.

This integration also covers JSONB object-key order, which must not reject an otherwise identical persisted CRDT. Admission compares canonical content after the same legal-to-editor projection used by clients. Empty/adjacent text runs normalize as in the editor; differing text, semantic IDs or formatting still fail. Read-only admission does not rewrite stored source. After a successful handshake the editor explicitly refreshes its editable DOM property before announcing readiness.

No database migration, credentials, provider settings or dependencies change. No private editor or encrypted relay is enabled. Existing production requirements in the deployment runbook still apply. The tests establish these source behaviors for the recorded browser and fixture environment, not hosted deployment, complete DCE-005/DCE-008 acceptance, every operating-system input method, or manual screen-reader acceptance.
